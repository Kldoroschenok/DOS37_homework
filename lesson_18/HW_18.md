## Задание 1: Запустить master-slave кластер postgresql (вручную или через repmgr)  

### 1. Подготовка окружения
Для выполнения задания были использованы две виртуальные машины в одной подсети:
- **Master (Primary):** `192.168.252.98` (Ubuntu 24.04, PostgreSQL 16.15)
- **Slave (Replica):** `192.168.252.90` (Ubuntu 24.04, PostgreSQL 16.15)

### 2. Настройка Master и статус
В файле [postgresql.conf](postgresql.conf):
- `listen_addresses = '*'` (разрешено принимать подключения по сети).
- `wal_level = replica` (уровень журнала для репликации).
- `max_wal_senders = 10`.

В файле [pg_hba.conf](pg_hba.conf) добавлено правило для доступа слейва:
```text
host    replication     all             192.168.252.90/32       trust
```

Статус на Master:  
```
postgres=# SELECT client_addr, state, sync_state FROM pg_stat_replication;
  client_addr   |   state   | sync_state
----------------+-----------+------------
 192.168.252.90 | streaming | async
(1 row)
```

Статус на Slave:  
```
postgres=# SELECT pg_is_in_recovery();
 pg_is_in_recovery
-------------------
 t
(1 row)
```

## Задание 4: Скрипт для проверки состояния Primary и Replica

Script conf: [check_db_status.sh](check_db_status.sh)

Скрипт выполняет три проверки:
1. Подключение к Primary (Master) и выполнение тестового запроса.
2. Подключение к Replica (Slave) и проверка, что она находится в режиме восстановления (`pg_is_in_recovery`).
3. Проверка статуса репликации на Master (команда выполняется от имени суперпользователя `postgres`, так как обычный пользователь не имеет прав на чтение таблицы `pg_stat_replication`).

### Результат работы скрипта:  
```

2. Replica (192.168.252.90): UP (in recovery / read-only)
3. Replication status (on Master): STREAMING (Working)
====================================
```
